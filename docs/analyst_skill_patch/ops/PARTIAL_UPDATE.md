## R-1 (остаточный риск платформы)

У `UpdateSkill` нет operation id, pending/status poll, гарантии порядка и
условной записи (etag/if-match). Диск — зеркало, не доказательство
сервера. **Доказуемо безопасный retry невозможен.**

Процедура **не объявляет** состояние `SAFE` в смысле «late overwrite
исключён». После любой неоднозначности — `UNKNOWN_PENDING` и решение
владельца. Таймер сам по себе не доказывает отсутствие поздней записи.

**TOCTOU:** между precondition-проверкой SHA на диске и вызовом
`UpdateSkill` нет атомарного compare-and-swap / etag. Чужая запись или
синхронизация в этом окне возможны; H-2 сужает, но **не устраняет** гонку.
Платформенного CAS нет — остаточный риск входит в R-1 и не объявляется
закрытым эвристикой «проверили только что».

## Инвариант записи (H-1 + H-2)

Глобально **одна** изменяющая операция `UpdateSkill` в полёте на всю
операцию `deploy_op_id`. Не параллелить id.

Перед **каждым** `UpdateSkill` (прямым или откатным):

1. Read-only: прочитать файл ресурса на диске.
2. Пересчитать sha256 (для skill — также `compare_skill_md` с ожидаемым
   текстом, если цель — тело tip).
3. Сравнить с **precondition SHA** для этого шага:
   - прямая запись: равен baseline строки таблицы;
   - откатная запись: равен «после прямой записи» этой же строки.
4. Несовпадение → **стоп без записи** этого ресурса; эскалация владельцу.
   Не подставлять «ближайший» текст.

После отправки `UpdateSkill`:

- Ответ `Updated` **не** равен apply.
- Подтверждение: диск совпал с ожидаемым post-write (sha /
  `compare_skill_md`) **и** sha стабилен ≥ **10 минут** с момента
  появления целевого текста (окно стабильности отдельно от окна ожидания
  появления; истечение любого таймера **не** доказывает отсутствие late
  write — см. R-1).
- Пока apply не подтверждён → состояние ресурса **`UNKNOWN_PENDING`**.
- Отсутствие нового содержимого на диске **не** значит, что операция
  отменена или провалилась.
- В `UNKNOWN_PENDING` для любого из трёх id: **запрещены** все новые
  `UpdateSkill` (включая «слепой» rollback вторым вызовом) и любые
  записи других ресурсов этой операции, пока владелец не снимет состояние.

Выход из `UNKNOWN_PENDING` — **только решение владельца** по фактам
read-only (диск + при необходимости Skill API как смысловой канал, не
как побайтовое доказательство; видимость Аналитику — проверка Даниила).
Варианты: «продолжить вперёд» / «пытаться откат после появления текста и
стабилизации» / «отменить операцию, пометить как не доказано».

## Последовательность прямой операции

Запись в `ops/ledger.md` до старта (`deploy_op_id`, tip SHA, supersedes
`pa-20261023-2122` при повторе).

1. Baseline read-only всех трёх + yaml. Иное — стоп.
2. Backup текстов трёх ресурсов в `$BK` + манифест sha (noclobber).
3. **OPT-6:** precondition check (H-2) → один `UpdateSkill` OPT → ждать
   подтверждение + стабильность. Иначе `UNKNOWN_PENDING(OPT)`.
4. **POS-4:** только если OPT подтверждён. Precondition check →
   `UpdateSkill` POS → подтверждение + стабильность. Иначе
   `UNKNOWN_PENDING(POS)`.
5. **skill v2.5:** только если OPT и POS подтверждены. Precondition
   check → один `UpdateSkill` `cli-analyst-bundle` → подтверждение +
   стабильность. Иначе `UNKNOWN_PENDING(skill)`. После этого шага
   **нет** последующих OPT/POS writes в рамках этой операции
   (асимметрия: skill последний).
6. Финальная сверка: три ресурса, yaml, description/QC/SPEC без изменений
   (sha), при возможности `find -newer` по allowlist. Skill API —
   смысловая сверка заголовка v2.5.
7. Статус handoff: `verified` только если все три post-write
   подтверждены и стабильны **и** владелец принял остаточный R-1.
   Иначе не писать `SAFE` / не считать late overwrite исключённым.

## State machine (кратко)

| Состояние ресурса | Смысл |
|-------------------|--------|
| `BASELINE` | sha = baseline, записи этой операции ещё не касались |
| `PENDING_WRITE` | `UpdateSkill` только что отправлен, apply не подтверждён |
| `CONFIRMED` | post-write sha/`compare_skill_md` ok и стабильность ≥10 мин |
| `UNKNOWN_PENDING` | был принят write (`Updated` или эквивалент), целевой текст не подтверждён или нестабилен; late write возможен |
| `FAILED_PRECONDITION` | H-2 стоп до отправки |

Переходы: `BASELINE` --precheck ok + UpdateSkill--> `PENDING_WRITE`.
`PENDING_WRITE` для запрета записей **эквивалентен** `UNKNOWN_PENDING`
(немедленный стоп любых других `UpdateSkill`), пока диск не даст
`CONFIRMED` либо владелец не снимет состояние. Если целевой текст не
появился / нестабилен после окна наблюдения — явно фиксировать
`UNKNOWN_PENDING` (не «failure» и не «success»). Из `UNKNOWN_PENDING`
записью **не** выходят; только решением владельца + последующими
наблюдениями. Автоматический retry `UpdateSkill` запрещён.

## Rollback / остановки по фазам операции

### A. Остановка до первой записи

- Известно: все три = baseline.
- Разрешено: только read-only.
- Rollback: не нужен.
- Запрещено: любой `UpdateSkill`.
- Конечное: да, baseline достоверен в пределах R-1 зеркала.

### B. OPT изменён (CONFIRMED), POS ещё нет

- Известно: OPT = post-write; POS, skill = baseline.
- Разрешено: продолжить POS (шаг 4) **или** откат OPT: precondition
  sha OPT == post-write → `UpdateSkill(OPT backup)` → ждать
  `CONFIRMED` baseline. Пока откат pending → `UNKNOWN_PENDING(OPT)`,
  стоп всех записей.
- Запрещено: писать POS/skill; второй write OPT без подтверждения.
- Конечное: только после `CONFIRMED` целевого направления (вперёд или
  откат) + решение владельца при R-1.

### C. OPT и POS изменены (оба CONFIRMED), skill ещё не вызван

- Известно: OPT/POS = post-write; skill = baseline. Промежуточная
  совместимость с v2.2 — см. выше (исключения инертны).
- Разрешено: продолжить skill **или** откат в порядке **POS → OPT**
  (каждая: precondition post-write → UpdateSkill backup → confirm).
  Skill не трогать, если не писали.
- Запрещено: UpdateSkill skill «на всякий случай»; параллельные откаты;
  файловый restore.
- Конечное: как в B для затронутых id.

### D. UpdateSkill skill вызван и применение CONFIRMED

- Известно: все три = post-write.
- Разрешено: финальная сверка; при отказе владельца — откат в порядке
  **skill → POS → OPT** (каждая с H-2 precondition = post-write и
  ожиданием confirm).
- Запрещено: новые «улучшающие» writes вне плана; объявлять отсутствие
  late overwrite.
- Конечное: `verified` только после стабильности всех трёх и принятия R-1.

### E. UpdateSkill skill вызван, состояние `UNKNOWN_PENDING(skill)`

- Известно: OPT/POS уже CONFIRMED post-write; skill — неопределён
  (v2.5 может появиться поздно).
- Разрешено: **только** read-only мониторинг; эскалация владельцу.
- Запрещено: любой новый `UpdateSkill` (в т.ч. rollback skill и любые
  OPT/POS); объявлять rollback/success/baseline «окончательными»;
  считать timeout failure или success.
- Конечное: **нет**, пока владелец не снимет `UNKNOWN_PENDING` по
  наблюдениям. Возможные исходы после появления текста: (1) стабильный
  v2.5 → как D; (2) стабильный снова baseline (если платформа так
  схлопнула) → задокументировать, не считать доказанным без стабильности;
  (3) текст так и не стабилизировался → операция незакрыта.

Аналогично: если `UNKNOWN_PENDING` на OPT или POS на шагах 3–4 —
дальнейшие ресурсы **не** писать (в т.ч. не вызывать skill).
